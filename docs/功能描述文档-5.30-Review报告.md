## A 类 — 严重 / 自相矛盾

### A1 🔴 `已锁车` 状态自相矛盾,代码事实上已自动锁车

- **位置**:文档 H4(第 414 行)/ 决策项 21 / 车辆状态字典(第 1021 行);代码 `app.py:3325`
- **文档现写**:决策项 21、H3(第 407 行)、变更日志第 1158 行均明确"T+7 后**只提示锁车,不自动锁**";车辆状态字典(第 1021 行)只列 `在库/报单锁定中/租赁中/以租代售/维修中/退车中/待维修/二手车/已售/已过户`,**没有 `已锁车`**。
- **问题**:`app.py:3325` 在 `lock_request` 审批通过分支里执行了
  ```python
  c.execute("UPDATE vehicles SET status='已锁车' WHERE id=?", (lr['vehicle_id'],))
  ```
  这与文档存在**两处矛盾**:① 代码写入了一个状态字典里不存在的值 `已锁车`;② "审批通过即改 `vehicles.status='已锁车'`"本质上就是系统侧的自动锁车动作,与"不自动锁车,仅提示"的业务口径相反。
- **改法建议**(二选一,需业务确认):
  - 若业务确实**保留人工锁车审批流**(锁车请求→审批→执行):应在车辆状态字典正式补入 `已锁车`,并修订 H4/决策项 21 措辞为"H1/H3 不自动锁车;锁车需经 `lock_requests` 审批",消除"不自动锁"与"审批即锁"的歧义。
  - 若业务坚持"系统永不改车辆锁定状态":删除 `app.py:3325` 的 UPDATE,锁车请求审批只产出线下通知。
  - 无论哪种,文档与代码必须就 `已锁车` 是否为合法状态达成一致。

### A2 🟠 H1 触发方式与代码实现不符(Cron 端点不存在)

- **位置**:文档 H1(第 319~320 行);代码 `app.py:1019/1046/2085/2158`
- **文档现写**:"系统每日 00:30…**触发**:Cron 调度 `POST /api/jobs/daily-collect`"。
- **问题**:实测 `grep daily-collect app.py` **无任何匹配**,该端点不存在。`check_overdue()` 的真实调用点是 `app.py:1046`(看板统计 `get_stats`)、`2085`、`2158` —— 即**用户访问页面时同步触发**,不是定时任务。这意味着:① 无人访问则当天不计提滞纳金、不推进状态;② 文档承诺的"00:30 日终批处理"在当前实现里并不存在。
- **改法建议**:要么补建 `POST /api/jobs/daily-collect` 端点 + 外部 Cron,把 H1 的状态机逻辑收口到这一个入口;要么把 H1 文档改为"由 `check_overdue` 在关键查询入口惰性触发",并明确说明其局限(依赖访问、可能漏跑)。当前 v3 已把 `check_overdue` 重写列为"代码改造提示",建议把"触发方式"一并纳入改造范围。

## B 类 — 规则缺口

### B1 🟠 H1 `临近还款` 判定方向倒置

- **位置**:文档 H1(第 336~337 行)、还款状态字典(第 1029 行)
- **文档现写**:
  ```
  diff = today - due_date          # 负数=未到期,正数=已逾期
  diff ≤ -3   且 status ∈ {待还款}  → status = '临近还款'   # T-3 及更早预警
  ```
- **问题**:`diff = today - due_date`,则 `diff ≤ -3` 表示**距到期还有 ≥3 天**(含还有 100 天、还有 1 年)。把"离到期还很久"判定为"临近还款"语义恰好相反。真正的"临近(T-3 窗口)"应是 `-3 ≤ diff < 0`(还剩 0~3 天)。当前写法会导致**所有远期未到期单子一上线就被标成"临近还款"**,T-3 预警形同虚设。
- **改法建议**:把临近还款条件改为 `-3 ≤ diff < 0`(或按业务定义的 `-3 ≤ diff ≤ -1`);`diff < -3` 的单子保持 `待还款` 不动。状态字典第 1029 行"`diff ≤ -3`"同步改正。

### B2 🟡 `待催款` 在到期前 2 天即触发

- **位置**:文档 H1(第 338~339 行)
- **文档现写**:`-3 < diff < 3 且 status ∈ {待还款,临近还款,部分核销} → status='待催款'`。
- **问题**:`-3 < diff` 即 `diff ≥ -2`,意味着**到期前 2 天**就进入"待催款",而 H2 催款文案默认客户尚未逾期。在应还日之前就把单子推入催款队列,与"T+3 才催"的整体节奏冲突,也会和 B1 的临近窗口重叠打架。
- **改法建议**:明确各区间边界互斥且符合业务语义,建议:`diff < -3`→`待还款`;`-3 ≤ diff < 0`→`临近还款`;`0 ≤ diff < 3`→`待催款`(到期未还、等运营 T+3);`3 ≤ diff < 7`→`T+3运营已催`;`diff ≥ 7`→ T+7 终态分流。把所有边界统一成左闭右开,消除 `<`/`≤` 混用。

### B3 🟠 F3 客户 24 期 / 厂家 36 期逐期勾稽缺口(保留未决项)

- **位置**:文档 F3(第 265~269 行,标注"⑤ 已知问题,本期保留")
- **文档现写**:客户常 24 期、厂家常 36 期,期数天然对不上;本期"保留现状,不做期数对齐 / 不做插值映射",维度 1(总额 ε 容差)+ 维度 3(首末期落点)通过即放行,中间期次交财务人工判断。
- **问题**:这是文档**自己已声明保留**的业务规则缺口,非笔误。但需提醒:在期数映射缺失的前提下,H1 按客户表 `repayments` 逐期计提滞纳金、H3 按客户期抵冲,而厂家回款按 `factory_repayments` 36 期走,两侧**逐期对账无法勾稽**。一旦未来需要"厂家逐期回款核对",当前数据结构(双表无期数映射)无法支撑,属于敞口风险。
- **改法建议**:维持本期保留决定即可,但建议在文档显式记录"未决项 owner 与目标版本"(如:折算口径需老板/财务确认后落 v4),避免长期悬挂。若短期内有厂家逐期核对诉求,需先补"期数映射表"或统一期数。**此项需业务方确认,不在文档/代码可自行闭环范围内。**

### B4 🟠 租赁合同末期"走 M 退车"缺触发者定义

- **位置**:文档 N1(决策项 6 / ⑥,第 1189、1220 行)、模块 M1
- **文档现写**:"N1 触发条件加 `contract_type='销售'` 守卫;租赁合同末期走 M 退车,不进入 N1"。
- **问题**:v3 正确地把租赁合同挡在 N1(过户/结清)之外,但**没有定义租赁合同到期后由谁、在什么条件下触发 M1 退车**。以租代售有 N1 的自动结清(Σpaid ≥ Σamount)兜底,租赁却缺一个对称的"末期到达 → 提示/触发退车"机制。若无人手动发起 M1,租赁合同会停在最后一期 `已还款` 而合同与车辆状态(`租赁中`)永不收口。
- **改法建议**:在 M1 或 H1 补一条规则——当租赁合同最后一期核销完成(或 `due_date` 越过末期)时,系统生成"待退车"提示推送给运营/销售,作为 M1 的触发锚点。明确这是"提示触发"还是"自动进入退车中",并补入车辆/合同状态流转说明。

## C 类 — 实现偏差

### C1 🟠 `待首付款` / `首付已驳回` 不在状态字典

- **位置**:合同状态字典(第 1016 行);代码 `app.py:2422`、`app.py:3256`
- **文档现写**:`delivery_status` 仅列 `待审批 / 待出库 / 已出库`。
- **问题**:代码实际使用了字典外的值:
  ```python
  app.py:3256  UPDATE contracts SET delivery_status='待首付款' WHERE id=?
  app.py:2422  if contract['delivery_status'] not in ('待首付款', '首付已驳回'):
  ```
  即真实的出库流程是 `待首付款 → (首付已驳回) → 待出库 → 已出库`,文档字典少了 `待首付款`、`首付已驳回` 两态。G2/G3 的首付款门禁逻辑因此与字典脱节。
- **改法建议**:在合同状态字典补入 `待首付款`、`首付已驳回`,并在 G2/G3 出库门禁章节画出完整流转(含首付款审批驳回回退路径),与代码对齐。

### C2 🟡 附录 W 建表数 15 / 14 / 13 三处自相矛盾

- **位置**:附录 W1 标题(第 1072 行)、v3 变更日志 ⑧(第 1191 行)、W1 表体(第 1074~1090 行)
- **文档现写**:W1 标题写"全新建表(**15** 张)";v3 变更日志 ⑧ 写"列出 **13** 张待建表";W1 表体实际列 15 行,但第 15 行 `rent_waivers` 标注"**删除/不存在**"——真正待建是 **14** 张。
- **问题**:同一份文档三处数字(15/14/13)不一致。实测 `database.py` 现有 19 张表,W1 列出的 14 张(#1~#14)确实**全部缺失**,数字核验本身正确,问题纯粹是表述口径不统一。
- **改法建议**:统一为"14 张待建 +1 张废弃(`rent_waivers`)"。W1 标题改"14 张待建(另 1 张废弃)";变更日志 ⑧ 的"13 张"改为"14 张"(v3.1 ⑩ 已补 `role_pages`/`role_actions`,13→14,日志未同步)。

### C3 🟡 `check_overdue` 改造提示只点了 1 个调用点

- **位置**:文档 H1 代码改造提示(第 367 行);代码 `app.py:1046/2085/2158`
- **文档现写**:"`app.py:1018~1033` 当前 `check_overdue` 仅做'过期→逾期'一步,需重写为…diff 区间式状态机"。
- **问题**:改造提示只提到函数定义处。实测 `check_overdue()` 有 **3 个调用点**(`1046` 看板统计、`2085`、`2158`),且当前 SQL 仍把记录直接置为已被 v3 移除的 `逾期`(实测属实)。重写函数签名/行为后,这 3 处调用语义都会变,迁移时需一并核对。
- **改法建议**:在改造提示补充"另需复核 3 处调用点(`app.py:1046/2085/2158`)的触发时机";并结合 A2,把"惰性触发"是否改为"Cron 端点"一并决策。

## D 类 — 次要

### D1 🟢 滞纳金 `diff ≥ 1` 即计提,与宽限期口径未对齐

- **位置**:文档 H1(第 340~341 行)
- **文档现写**:`diff ≥ 1 且未结清 → 写/更新 late_fee_ledger 当日累计行`。
- **问题**:`diff ≥ 1` 即逾期第 1 天就计提万 5/日滞纳金,但 H1 同时存在"T+3 才催、T+7 才抵冲"的节奏。是否有 1~3 天宽限期(到期后几天内还款不收滞纳金)文档未明确。若业务有宽限期,起算点应后移。
- **改法建议**:明确滞纳金起算 diff(无宽限=`diff ≥ 1`;有宽限=`diff ≥ 宽限天数+1`),在 H1 与决策项 5 处统一写死,避免实现时各取一值。

### D2 🟢 `临近还款` 状态机标记 与 T-3 手动提醒动作关系未理清

- **位置**:文档 H1(第 337 行状态机 / 第 365 行手动发送提醒)
- **文档现写**:状态机把单子自动标 `临近还款`;同时运营在工作台手动点【发送提醒】发短信/微信并写 `notification_logs`。
- **问题**:两者都围绕 T-3,但文档未说明状态 `临近还款` 是否就是"出现在'今日 T-3 预警'列表"的依据。若列表用 diff 实时算、状态机又单独标记,可能出现"状态已临近但列表未列"或反之的口径不一致。
- **改法建议**:明确"今日 T-3 预警列表"的数据来源(建议直接以 `status='临近还款'` 为准),让状态机标记与工作台列表同源。
