## A 类 — 严重 / 自相矛盾

### ① F3 归一化公式数学冗余,且与"允许利差"自相矛盾

**位置**:v2 第 245–251 行

**文档现写**:

```
1. 总金额一致:Σ factory.amount ≈ Σ customer.amount(允许利差/管理费区间)
2. 跨期归一化金额:
   normalized_factory_per_period
     = (Σ factory.amount × factory_periods⁻¹) × (factory_periods / customer_periods)
     ≈ Σ factory.amount / customer_periods
```

**问题**:
- **数学冗余**:`× factory_periods⁻¹ × factory_periods` 前后抵消,化简后恒等于 `Σ factory.amount / customer_periods`,前半段乘除毫无作用。
- **与维度 1 自相矛盾**:维度 1 明确"允许利差/管理费区间"⇒ 客户表本就含利差。维度 2 用"厂家总额 ÷ 客户期数"和客户单期 `rent` 直接比,只要存在利差,**维度 2 必报"差异"**,与维度 1 的容差设定打架。

**改法建议**:

```diff
  1. 总金额一致:Σ factory.amount ≈ Σ customer.amount(允许利差/管理费区间 ε)
- 2. 跨期归一化金额:normalized = ... ≈ Σ factory.amount / customer_periods
+ 2. 单期均值参考(仅展示,不参与判定):
+    factory_avg = Σ factory.amount / factory_periods
+    customer_avg = Σ customer.amount / customer_periods
+    展示 (customer_avg - factory_avg) 作为"利差/管理费/期"参考值
  3. 首末期日期一致:...
```

让维度 2 退化为展示项,判定只看维度 1 + 维度 3。

### ② 逾期单被日终批处理"漏看"——文档自相矛盾 + 代码缺状态机

**位置**:v2 第 299 行 vs 第 918 行;`app.py:1018-1033`

**文档第 299 行(H1 步骤 1)**:

```
拉取所有未结清 repayments(status ∈ {
  待还款, 临近还款, 部分核销, 待催款,
  T+3运营已催, T+7销售已催, 逾期    ← 老的
})
```

**文档第 918 行(状态字典)**:

```
v2 把"逾期"细化为两态:
  逾期-资金池可冲
  逾期-资金池耗尽
移除了泛化的"逾期"
```

**两处直接打架**。结果:已进入新两态的单子,**永远不再被 H1 扫描**——不计提滞纳金、不再尝试抵冲、不再推送催款,这条单"消失"在系统里。

**代码侧雪上加霜**(`app.py:1018-1033` `check_overdue`):

```python
# 当前代码做的:
UPDATE repayments SET status='逾期'
WHERE status IN ('待还款', '部分核销') AND due_date < today
```

只有一个粗暴的"过期 = 逾期"。文档要求的状态:
**临近还款 / 待催款 / T+3运营已催 / T+7销售已催 / 逾期-资金池可冲 / 逾期-资金池耗尽**——**代码里一个都不会进入**,而代码用的"逾期"在 v2 状态字典里**已不存在**,跑出的是文档不认的"幽灵状态"。

**改法**:

第一步,文档 line 299 改成:

```diff
- status ∈ {..., 逾期}
+ status ∈ {..., 逾期-资金池可冲, 逾期-资金池耗尽}
```

第二步,`check_overdue` 重写成按"逾期天数"分流的状态机:

```
今天 - due_date
  -3  → 待还款 → 临近还款
   0  → 待还款/临近还款 → 待催款
   3  → 待催款 → T+3运营已催(待催)
   7  → T+3运营已催 → T+7销售已催(待催),触发 H3
  >7  → 资金池>0 ? 逾期-资金池可冲 : 逾期-资金池耗尽
  ≥1  → 同步写 late_fee_ledger 当日累计行
```

### ③ J3 减免 ↔ H3 抵冲时序竞态

**位置**:v2 第 329–356 行(H3) + 第 422–442 行(J3)

**问题**:
- J3 是异步多步流程:销售发起 → 老板审批 → 财务执行;
- H3 是 T+7 日终批处理自动动作;
- 决策项 12 只定义了**"已审批减免"**和**"未减免"**两态的处理。

**漏掉了第三态**:T+7 时点减免申请处于 `待审批` 中。会出现:
1. T+7 当天,H3 把这笔滞纳金当应收抵冲(从押金扣) ✅
2. 第二天老板批准减免 ✅
3. 财务执行减免,在 ledger 上标 `waived_amount` ✅
4. **同一笔滞纳金"既被抵冲又被减免",资金池被重复扣**

**改法**:在 H3 抵冲前增加守卫——

```
对每笔 late_fee 抵冲前,检查:
  存在 waivers(target=该期, waiver_kind='late_fee', status='待审批') ?
    → 跳过本次抵冲,标记"待减免审批,本期暂不冲"
    → SLA 24h 仍未批 → 默认按"未减免"处理,正常抵冲
```

## B 类 — 规则缺口

### ④ 以租代售资金池可能恒为 0,H3 实际被架空

**位置**:v2 第 331–332 行

**文档现写**:

```
H3 抵冲资金池:
  租赁:押金(contracts.deposit_paid,1~1.5 倍月租)
  以租代售:首付款剩余可用部分(若约定预留缓冲)
```

**问题**:以租代售首付款通常**全额用于购车、无缓冲** ⇒ 资金池 = 0 ⇒ 决策项 13"上限=资金池余额"立即触发"资金池耗尽"。等于以租代售逾期从 T+7 第一天就跳过抵冲直入 `逾期-资金池耗尽`,H3 形同虚设。

**改法**:文档需在 H3 明确以租代售下:
- 是否要求合同条款必须保留首付缓冲(并定下默认比例,如月供 × N 倍);
- 或者让"客户预收"(`customer_prepayments`)升级为以租代售场景的主资金池;
- 或者直接说明"以租代售场景 H3 仅扣预收余额,无预收即直接进 `资金池耗尽` 状态"。

三选一,需业务方拍板。

### ⑥ N1 自然结清未按业务类型过滤,租赁合同会被错误生成过户单

**位置**:v2 第 620–625 行;database.py:160 `contracts.contract_type`

**文档现写**:

```
N1 自然结清
触发:I 模块某一期核销后,系统检测
      Σ paid_amount ≥ Σ amount  且  period == loan_periods
动作:① 财务复核结清
      ② 创建 ownership_transfers(status='待过户')
      ③ 推送运营
```

**问题**:不区分 `contract_type`。租赁合同(车要还回来)末期还完款的瞬间,会被自动开一张过户单,运营被误导,后续还要走 M 退车,出现"既待过户又待退车"的状态冲突。database.py:160 中 `contract_type` 默认 `'租赁'`,大部分合同会踩中。

**改法**:

```diff
  N1 自然结清
- 触发:Σ paid ≥ Σ amount 且 period == loan_periods
+ 触发:同时满足:
+       ① contracts.contract_type = '销售'(即以租代售)
+       ② Σ paid_amount ≥ Σ amount
+       ③ period == loan_periods
+
+ 注:contract_type = '租赁' 的合同末期还完款后,走 M 模块退车流程,
+    不进入 N1,不生成过户单。
```

代码侧 I2 末期核销触发 N1 的位置同步加 guard:

```python
if 末期核销完成 and contract['contract_type'] == '销售':
    创建 ownership_transfers
    推送运营
```

### ⑦ I2 多还"预抵" ↔ H3 费用优先级冲突

**位置**:v2 第 334–338 行(H3 优先级) vs 第 383–386 行(I2 多还)

**问题**:
- I2 多还把富余款按客户确认月份置后续 N 期为 `预抵`,**只顺延租金期**;
- H3 抵冲优先级却是:保险/代办 > 维修/罚金 > 本期租金 > 滞纳金;
- 若客户尚有未付保险费/滞纳金,I2 直接预抵未来租金,**跳过 H3 中更高优先级的应收**;
- 同一笔富余资金被两套分配逻辑给出不同归属。

**改法**:I2 多还分支前,先按 H3 优先级清偿现存未付应收,清偿后剩余金额才按客户确认月份做"预抵"。文档需明确"先冲应收再预抵"这条铁规。

### ⑨ 决策项 30 的 RENAME 迁移必然报错

**位置**:v2 第 428 行

**文档现写**:

```sql
ALTER TABLE rent_waivers RENAME TO waivers;
```

```sql
    reason TEXT,

    sales_applied_by TEXT, sales_applied_at TEXT,
    boss_approved_by TEXT, boss_approved_at TEXT,
    finance_reviewed_by TEXT, finance_reviewed_at TEXT,
    attachment_path TEXT,
    FOREIGN KEY(contract_id) REFERENCES contracts(id)
```

### ⑤ G2 → G3 写回:代码已正确处理,文档漏写一句说明

**唯一问题**:v2 文档 G2 财务侧只写了改 `contract_initial_payments`,没写"同步写回 contracts 三个字段"。

**补充建议**:在 G2 财务侧规则后追加一句:

> 财务审批通过时,系统同步写回 `contracts.down_payment_status='已收'`、`deposit_status='已收'`(租赁含押金)、`delivery_status='待出库'`,G3 出库据此校验。

**附带措辞统一**:代码里收款单审批后状态值是 `已通过`,文档写的是 `已审批`,建议文档统一为 `已通过` 与代码对齐。
